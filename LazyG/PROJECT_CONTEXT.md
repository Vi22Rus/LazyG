## 1. Назначение и главный выбор архитектуры

LazyG — **единая расширяемая Windows-программа** на C#/.NET 8 WPF для множества версий World of Warcraft, включая официальные и приватные серверы. **Первой целевой платформой является WoW Forever**; собственный Lua-аддон для неё — только первая реализация. Для каждого поддерживаемого клиента/версии нужны совместимый Lua-аддон и соответствующие XML-ротации. Отдельные Windows-программы под каждую версию НЕ создаём. Проект развивается по **принципу разделения обязанностей WarMate + его аддона Sertyrew**:

```text
World of Warcraft Forever
  -> собственный Lua-аддон LazyG (сбор доступных игровых состояний)
  -> компактный RGB-пакет на краю игрового экрана
  -> Windows LazyG.exe (захват маленькой зоны, декодирование, состояние игры)
  -> собственный движок выбора ротации + определения ротаций в XML
  -> рекомендация/сопоставленная клавиша (этап будущей реализации)
```

**РЕШЕНО:** ротационный движок должен работать на стороне Windows; Lua-аддон НЕ хранит полные ротации и НЕ вычисляет весь список приоритетов. Lua собирает необходимые игровые данные через допустимый WoW API и отдаёт их через RGB. Windows декодирует и оценивает условия. НЕ переносить интерфейсы/исходники WarMate и Sertyrew как собственные.

**НОВОЕ ЯВНОЕ ТРЕБОВАНИЕ ПОЛЬЗОВАТЕЛЯ (2026-11-18): ротации обязательно оформлять в XML-файле/файлах.** Это формат *данных ротаций LazyG*, не YAML WarMate и не Lua Sonah. Конкретная XML-схема, дерево файлов, механизм парсинга/валидации и упаковка **ЕЩЁ НЕ РЕАЛИЗОВАНЫ**. Совместить с более ранним решением «ротации внутри EXE»: хранить читаемые XML-исходники в GitHub, при сборке включать XML как ресурсы в единый EXE, загружать из ресурсов во время работы; не требовать устанавливать внешний набор XML пользователю. Решение об отдельном импортируемом XML можно принять позже, но исходная поставка — один EXE. **Пока НЕ шифровать и НЕ вводить ключи**; возможность последующего шифрования/лицензирования оставить архитектурно, но не внедрять сейчас. Не объявлять XML уже встроенным: это задание на будущее.

Главная идея: своя реализация, воспроизводящая *игровое поведение, условия и приоритеты* референсных ротаций, не копируя чужие защищённые фрагменты кода и оформления.

## 1.1. Обязательная многоверсионная архитектура — подтверждено пользователем 2026-11-18

**Долгосрочная цель:** ОДНА устанавливаемая Windows-программа `LazyG.exe`, которая со временем поддерживает **все необходимые версии World of Warcraft**, включая официальные клиенты, разные расширения, приватные серверы и, в частности, **WoW 3.3.5**. Первая реализуемая ветка — WoW Forever, но весь новый код проектировать с расчётом на расширение. Нельзя строить Windows-ядро так, чтобы для 3.3.5 потребовалось копировать всю программу, создавать второй EXE или переписывать движок с нуля.

- **Один общий Windows Core:** GUI, управление профилями и назначениями клавиш, получение RGB-данных, проверка целостности пакета, модель игровых состояний, механизм условий и оценки приоритетов, механизмы установки и обновления совместимого Lua-аддона.
- **Версионные адаптеры:** у каждого семейства клиента/сервера отличаются `Interface`, Lua API, доступность/защищённость полей, идентификаторы заклинаний, таланты, ауры, GCD, ресурсы и правила классов. Поэтому нужны изолированные реализации сбора данных и адаптеры протокола/нормализации, без вызова API конкретной игры в общем Windows-движке.
- **Отдельные Lua-аддоны под конкретные клиенты/версии:** установка из той же Windows-программы; имя, версия, TOC, файлы и набор доступных сигналов определяются выбранным профилем клиента. У каждого аддона одна роль: собирать игровые состояния и передавать их через RGB, а не содержать ротации.
- **Разные ротации для разных версий — обязательно XML:** отдельные наборы XML правил для каждого типа клиента/сервера, при необходимости с уточнением билда, уровня, класса, специализации и режима боя. **Нельзя считать, что Hunter или SpellID одинаковы в Forever, 3.3.5 и других клиентах.** Приоритеты из Sonah относятся прежде всего к Forever; для 3.3.5 и остальных версий выбирать и проверять собственные релевантные игровые референсы, включая доступные NAG/Hekili/другие материалы. Все XML входят в единый EXE как ресурсы при сборке (до появления другой явной договорённости); не смешивать наборы правил разных версий.
- **Идентификация клиента и совместимости:** перед загрузкой XML-правил и декодированием RGB Windows должен знать целевую версию клиента и версию установленного аддона/протокола. Предусмотреть осмысленные идентификаторы, протокольную версию и набор поддерживаемых полей (capabilities). Не трактовать неподдерживаемое игровое поле как `false`, `0` или «заклинание недоступно», если оно фактически не было получено.
- **Расширение без регрессий:** добавление клиента 3.3.5 или нового приватного сервера должно преимущественно означать создание нового набора Lua-адаптеров, XML-правил и описания версии, а не изменение уже проверенного поведения Forever. Регрессионные тесты и контрольные сборки для каждой поддерживаемой версии обязательны по мере расширения.
- **Не делать неподтверждённых предположений:** общая архитектура согласована, но версионный каталог, общий контракт состояния, XML XSD, подключаемые пакеты, механизм определения сервера и UI выбора версии пока НЕ реализованы. Их нужно проектировать до массового портирования ротаций.

Ориентировочная **будущая**, а не существующая структура:
```text
LazyG/
  Windows/
    Core/                 # нормализованная модель состояния, XML-движок, интерфейс
    ClientProfiles/       # реестр версий/серверов, совместимость, протоколы
    Rotations/
      Forever/            # XML для Forever
      WoW335/             # XML для WoW 3.3.5
      ...                 # другие версии/серверы
  Addons/
    Forever/              # собственный Lua-аддон для Forever
    WoW335/               # собственный Lua-аддон для 3.3.5
    ...                   # будущие реализации
```
Не переносить текущие файлы в эти папки без отдельного запроса. Сейчас существуют `LazyG/AddonTemplate/` и `LazyG/Windows/`; это лишь иллюстрация целевой модульности.

**Правило для каждого нового задания:** если изменение относится только к Forever — размещать его в адаптере Forever или в соответствующем наборе XML. В общее ядро включать только действительно универсальное поведение. Версии клиентов, манифесты, ID и специфику API держать в версионных данных/адаптерах, не хардкодить единственную Forever-логику в глобальные компоненты.

## 2. На что ориентируемся

### WarMate + Sertyrew — РЕФЕРЕНС АРХИТЕКТУРЫ И ПЕРЕДАЧИ ДАННЫХ

Пользователь ранее предоставил:

- `WarMate_Encrypted_Rotation_Profiles.zip` — около 60 файлов `*.yaml.enc`, в т. ч. `profiles/hunter/beast_mastery/beast_mastery.yaml.enc`, PvP-варианты и другие классы.

Подтверждённые пути по архиву Sertyrew:
- `Sertyrew/Collect/Player.lua`, `Target.lua`, `Spells.lua`, `Auras.lua`, `Spec.lua`, `Talents.lua`, `Traits.lua`, `Trinkets.lua`, `Enemies.lua`, и др. — сбор игровых фактов;

Вывод: архитектуру разделения «сбор данных → RGB → Windows» можно изучать и воспроизвести собственной реализацией. Зашифрованные профили подтверждают наличие внешних данных ротаций WarMate, **но точный алгоритм работы EXE и содержимое зашифрованных профилей НЕ подтверждены**. Не писать, что мы «расшифровали» их или доказали, что абсолютно все решения в EXE. Адаптация Sertyrew 3.3.5 к WoW Forever не является копированием: API заметно различаются.

**Место файлов:** пользователь добавляет исходные архивы в **Файлы проекта ChatGPT Lazy**. Они могут оказаться доступны через файлы проекта, но автоматической синхронизации с GitHub нет. На дату создания этого файла референсных бинарных архивов в репозитории под `References/WarMate` НЕ проверено. Новые чаты: сначала пробовать доступные файлы проекта/Library, затем спрашивать о файле, только если действительно недоступен. Не утверждать, что архив автоматически существует в GitHub. При необходимости хранить ссылки и описания без публикации чужого бинарного содержимого.

### Sonah — ГЛАВНЫЙ РЕФЕРЕНС ПОЛНОТЫ РОТАЦИЙ

Пользователь предоставил `Sonah.7z` (более старый) и **`Sonah.zip` (Forever 1.2.5)**. При разработке правил приоритетов ориентироваться на наиболее актуальный проверенный архив Sonah и сравнивать с игровой механикой WoW Forever. В ZIP реально существуют:
- `Sonah/Classes/Hunter.lua`, `Paladin.lua`, `Warrior.lua`, `Druid.lua`, `Mage.lua`, `Priest.lua`, `Rogue.lua`, `Shaman.lua`, `Warlock.lua` (9 классов);
- `Sonah/Classes/Racials.lua`;
- `Sonah/Core/Molecules/Conditions.lua`, `Sonah/Core/Organisms/Engine.lua` и другие состояния/условия.

**Пользователь требует ПОЛНОЕ покрытие всех боевых правил всех специализаций, без упрощённой десятки способностей.** Весь порядок приоритетов и все игровые предикаты (в пределах реально доступного API): выбор/жизнь/враждебность цели, дистанция, баффы/дебаффы/стаки/время действия, GCD, отдельные и общие кулдауны, ресурс, проки, движение, способности классов и рас, наличие/состояние питомца, одиночная и AoE-логика, PvE/PvP, защитные умения, хилпоты, камни здоровья, аксессуары, прерывания, снятие эффектов, другие расходники и важные исключения. Порог вроде «хилпот при HP < 15%» должен быть управляемым параметром и использовать доступные игровые факты, а не быть магическим числом, навечно вшитым в код. Реализовать поведение на собственной системе правил в XML и собственном движке на C#.

**ИСКЛЮЧИТЬ НЕБОЕВОЕ:** интерфейс Sonah, окна/стили, подсказки прокачки талантов и их отображение в окне талантов, дополнительную статистику и посторонние функции. Таланты СЧИТЫВАТЬ для выбора специализации и условий ротации, но НЕ давать игроку подсказки, какой талант качать.

**Права:** проверенный `Sonah/LICENSE` внутри `Sonah.zip` содержит All Rights Reserved и прямой запрет использования частей аддона в чужих проектах без разрешения. Пользователь считает, что автор позднее публично разрешал использование, но подтверждающего разрешения в текущих проверенных файлах нет. Общие игровые механики, игровые SpellID и функциональные требования можно реализовывать независимо; **не переносить дословно Lua-код или оригинальное выражение чужих списков правил**, не распространять Sonah как часть LazyG без ясного разрешения. Примеры поведения и проверка полноты допустимы как ориентиры для самостоятельной реализации. Не делать юридических заявлений об абсолютной свободе копирования.

### RGB: версии и конкретная раскладка

**0.1.11-dev, протокол v1, подтверждённая контрольная точка пользователем:**

- отмеченная проблема: для работы приходилось сбрасывать графические настройки WoW по умолчанию; это **не решено** и не должно стать постоянным требованием;
- этот PASS не доказывает работу на всех UI Scale и разрешениях.

**0.1.12-dev, протокол v2, последняя тестовая версия, НЕ подтверждена пользователем:**
- ровно **ОДНА** горизонтальная строка из 9 ячеек **4×4 UI-ед.**, промежуток 1, шаг 5, общий размер 44×4;
- первые четыре цветовых маркера `green|magenta|white|black`; далее `class/race/level`, `spec/points/version=2`, `flags/0/0`, контрольная сумма, конечный `magenta`;
- битовая маска `flags`: 1 — цель существует; 2 — цель враждебная/можно атаковать; 4 — цель жива; 8 — персонаж в бою. Некоторое недоступное или защищённое игровое состояние может ошибочно выглядеть как `false` — для будущего протокола нужны отдельные биты «известно/неизвестно»;
- события `PLAYER_TARGET_CHANGED`, `PLAYER_REGEN_DISABLED/ENABLED`, `UNIT_FLAGS`, `UNIT_HEALTH` и события персонажа;
- Windows показывает данные и флаги в Setup/Overview. В Overview обновление раз в 3 секунды, если окно игры активно; на фоне оно не гарантируется;
- `HP%`, энергия/мана/ярость, баффы, дебаффы, кд, GCD, способности и прочие сложные факты **пока не передаются**;
- код 0.1.12-dev собран в GitHub Actions, Windows startup smoke test прошёл. **В самой игре эта версия ещё не проверена**. Не называть релизом.
- GitHub Actions успешного EXE для 0.1.12-dev: https://github.com/Vi22Rus/LazyG/actions/runs/44275339864
- подтверждённая проверенная пользователем v1 0.1.11-dev: https://github.com/Vi22Rus/LazyG/actions/runs/44271870214

**Тестовый сценарий v2:** а) нет цели/нет боя → no,no,no,no; б) есть живая враждебная цель вне боя → yes,yes,yes,no; в) начать атаковать эту же цель → yes,yes,yes,yes; г) после смерти цели может быть yes,yes,no,combat yes/no. Не просить войти в бой «без цели», это была ошибка прежней инструкции.

Текущий RGB захват зависит от видимости окна WoW и его положения на переднем плане. Уменьшение до 4×4 может сделать обнаружение хуже при нестандартных настройках. Нужно проверить привычные графические настройки пользователя и масштабы, не требовать сбрасывать их. Работа с эксклюзивным fullscreen, DPI и изменением UI Scale не считается подтверждённой.

### Порядок загрузки аддона

Setup пишет `.toc` с `HunterProfile.lua` **перед** `Panel.lua` (Panel читает `LazyGHunter`). При обновлении всегда менять embedded Lua в `AddonTemplate.cs` вместе с отдельным Lua и проверять версию TOC. Установленный аддон сам не обновляется; для теста нужно новое имя или вручную обновить папку с сохранённой копией и выполнить `/reload`.

## 4. План XML-движка ротаций — СОГЛАСОВАННО, НО ЕЩЁ НЕ НАПИСАНО

**Требование к реализации:** все ротации — в собственном XML представлении; C#-движок парсит/валидирует XML, вычисляет приоритеты сверху вниз и выбирает следующую доступную способность. Обработчик условий должен быть общим для классов и не содержать больших веток `if Hunter ... elseif Mage` для каждой ротации. Отдельная таблица игровых фактов, отдельная модель команд/SpellID, отдельная модель назначения клавиш; чёткие признаки «неизвестно», «недоступно» и «ложь».

Пример *предполагаемого* дерева, НЕ существующих файлов:
```text
LazyG/Windows/Rotations/
  RotationSchema.xsd       # предлагаемая проверка XML; ещё не создана
  hunter.xml               # BM/MM/Survival, leveling/прочие режимы
  paladin.xml              # и остальные классы
  ...
```
Можно предпочесть один `Rotations.xml` либо несколько файлов по классу — **решение об окончательной структуре не утверждено**, но XML-формат обязателен. В выходном Windows EXE определения XML должны быть включены как ресурсы, чтобы не распространять отдельные файлы ротаций. Это будущая работа, не выдавать её за существующую функцию.

XML должен уметь выразить:
- селекторы: класс, специализация, уровень, известные заклинания, таланты, контекст PvE/PvP;
- условия: AND/OR/NOT, сравнения, кулдауны/заряды/GCD, дистанцию, баффы/дебаффы (стак/время), состояние питомца, ресурсы, hp, движение, AoE, состояние цели;
- действия: способность (SpellID), предмет (itemID), расовое, прерывание/защита, отсутствие рекомендации;
- приоритеты и их порядок, ограничения/таймеры использования расходников, конфигурируемые пороги;
- диагностический вывод: почему правило подошло или было пропущено, что неизвестно из-за API.
- безопасное поведение при неполном RGB-пакете: **не выдавать ложные рекомендации**.

Ротации должны воспроизводить полезное **игровое поведение** полного набора Sonah независимо, с тестами на конкретных игровых сценариях. Нельзя «сделать только Hunter BM» и объявить реализацию всех ротаций завершённой. Делать последовательно: сначала Hunter BM, затем MM, Survival, потом остальные классы, с явным списком покрытых условий и отчётом о пробелах.

**НЕ РЕАЛИЗОВАНО:** XML loader/schema, XML-ротации, вычислитель приоритетов в EXE, расширенная RGB телеметрия, синхронизация с назначенными клавишами, полная поддержка расходников. Сейчас только начальный RGB Bridge и диагностика.

## 5. Исторические требования к продукту — не путать с текущим прототипом

Если приоритет Healbot/Logitech будет перенесён в новую архитектуру, сохранить задуманные приоритеты, но основывать изменения на фактических исходниках и отдельном тесте. ## 7. Обязательные правила разработки

1. **Никакого изменения исходников без прямого запроса пользователя.** Документацию изменять по запросу и отмечать как docs-only.
2. Перед каждым кодовым изменением читать `LazyG/PROJECT_CONTEXT.md` и реальные файлы репозитория; дополнительные референсы искать в прикреплённых файлах проекта.
3. GitHub `Vi22Rus/LazyG` — главный источник текущих исходников. Не реконструировать код из памяти и не придумывать прежние тесты. Если в другом чате контекста не видно — опираться на этот документ, но проверять исходники.
4. Не путать три уровня: **проверено пользователем в WoW**, **собрано GitHub Actions/запустилось**, **запланировано, но не написано**.
5. Перед существенным изменением предусмотреть откат; не объявлять dev «релизом» или «stable» без пользовательского подтверждения.
6. Префикс **dev/development** для промежуточных версий. Релизное обозначение — только когда пользователь явно подтвердит.
7. Следовать ранее выбранной процедуре: по явному запросу изменять `main` (если нет другого указания), запускать GitHub Actions, проверять результат. Не утверждать успех до успешного workflow.
8. С каждой собранной Windows-версией давать прямую страницу соответствующего GitHub Actions artifact и команду PowerShell для сборки **единого EXE**:
   ```powershell
   dotnet publish LazyG/Windows/LazyG.csproj -c Release -r win-x64 --self-contained true -p:PublishSingleFile=true -p:IncludeNativeLibrariesForSelfExtract=true -p:DebugType=None
   ```
9. После каждого содержательного изменения обновлять этот файл: версию, изменения, SHA/ссылку на сборку, результат CI, результат тестирования пользователем и следующую задачу. Не смешивать подтверждённое/неподтверждённое.
10. Не загружать сторонние защищённые архивы в публичный или приватный репозиторий без осмысленной проверки прав на распространение. Референсы доступны в файлах проекта; если они не видны в новом чате, это честно сообщать, а не утверждать об их наличии.
