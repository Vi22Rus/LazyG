# LazyG RGB v3 — черновик wire-спецификации 0.1

**Дата:** 2026-11-18. **Статус:** DESIGN / DRAFT — **НЕ реализовано**, не проверено в WoW.  
**Основание:** [архитектурный план](RGB_PROTOCOL_V3_PLAN.md), текущий RGB v2 в `0.1.13-dev` и статическое изучение **Sertyrew.zip** (без запуска WarMate.exe).  
**Цель:** воспроизводимый бинарный протокол для собственного Lua encoder + C# decoder, пригодный для последующих PvE/PvP/XML-ротаций, со строгим запретом смешивать API WoW Forever и 3.3.5.

## 1. Проверенные свойства референса и границы заимствования

Непосредственно просмотрены `Sertyrew/Protocol/Protocol.lua`, `Encode.lua`, `Crc16.lua`, `Output/FrameAnchor.lua`, `Strip.lua`, `Core/Layout.lua` и `Profile/Profile.lua`. В **референсе Sertyrew**: protocol.version=1; coreCells=23; четыре начальных маркера; `cellPixels=3`, `maxCellsPerRow=96`; `direct8` (8 bits, step 1) и `stepped4` (4 bits, step 17); CRC polynomial `0x1021`, init `0xFFFF`, check `0x29B1`. `FrameAnchor` рассчитывает масштаб с учётом физической высоты и `UIParent:GetEffectiveScale()`. `Core/Layout` собирает набор блоков и таблиц по профилю.

Эти значения относятся **к архиву Sertyrew**, а **не** доказывают точное поведение закрытого Windows `WarMate.exe`. Далее описан **наш собственный** формат LazyG v3; он не является двоично совместимым с Sertyrew.

## 2. Совместимость и поведение декодера

- **RGB v2 сохраняется**: девять ячеек (4×4 UI, шаг 5) остаются прежними в существующем Lua/Windows `0.1.13-dev`. Новый пакет v3 размещается только в отдельной будущей dev-версии аддона. Не пытаться автоматически считать v2 как v3.
- Первая поддерживаемая схема v3 — `encoding=0` (`direct8`, три **байта** RGB на логическую ячейку). `encoding=1` зарезервирован для будущего `stepped4` и должен **отклоняться** v3.0-декодером до точного описания раскладки полубайтов, калибровки и тестовых векторов. Не выдавать зарезервированное за реализованное.
- Целевые клиенты: `clientFamily=1` Forever, `2` WoW 3.3.5 (**зарезервирован**). Для v3.0 идентификатор 2 можно только распознать и сообщить «нет адаптера», нельзя применять правила Forever.
- Полоска выводится по реальным пикселям с учётом проверенного эффективного масштаба. Размер 3 физ. пикселя из референса — **начальная гипотеза**, не жёсткое требование: до реализации нужны измерения на графических настройках пользователя. Никаких автоматических сбросов настроек WoW.
- Рендер и захват не гарантируют атомарности экрана. CRC и дублирование sequence сокращают риск принятия разорванного кадра, но не дают математической гарантии; при ошибке — отклонение snapshot.

## 3. Логическая раскладка прямого RGB-пакета v3.0 (проект фиксирован для тестовых векторов)

Каждая ячейка `(R,G,B)` даёт ровно **3 байта** с диапазоном `0..255`. Ячейки идут слева направо; если выход за строку необходим, переход на следующую строку выполняется после согласованного `cellsPerRow` в манифесте адаптера (нельзя угадывать это по изображению).

| Индекс | Назначение | R | G | B |
|---|---|---|---|---|
| 0 | Marker A | FF | 00 | FF |
| 1 | Marker B | 00 | FF | 00 |
| 2 | Reference white | FF | FF | FF |
| 3 | Reference black | 00 | 00 | 00 |
| 4 | Header 0 | Protocol version = 03 | Frame sequence (`u8`) | Encoding = 00 |
| 5 | Header 1 | Client family (`u8`) | Profile hash hi | Profile hash lo |
| 6 | Header 2 | Payload length hi | Payload length lo | Block count (`u8`) |
| 7 | Header 3 | Schema revision = 01 | Capabilities revision = 01 | Reserved = 00 |
| 8..N | Профильные блоки | См. ниже | | |
| N+1 | CRC footer | CRC16 hi | CRC16 lo | Повтор frame sequence |

**Payload length:** `u16` big-endian, число логических ячеек **между заголовком и CRC**, включая заголовки блоков. Это НЕ число байтов и не физическая ширина. Количество ячеек всего: `4 marker + 4 header + payloadCellCount + 1 footer = 9 + payloadCellCount`. Поле 0 допускается с `blockCount=0`.

**Frame sequence:** `u8` (0..255 по модулю 256); один snapshot имеет один номер в заголовке и footer. Наличие очередного номера не доказывает обновление игровых состояний — фиксируется freshness/время последнего валидного кадра. При чтении двух одинаковых кадров не нужно выдумывать изменение.

**Профиль:** `profileHash` — `u16` (big-endian), часть согласованного *манифеста* конкретного клиента/класса/специализации. При несовпадении словаря/профиля декодер выдаёт `incompatible profile`, а не неверную рекомендацию. Коллизии 16-битного хэша исключаются манифестом (уникальность в наборе + ревизия/capabilities); для сильной идентификации позднее потребуется более широкий hash/ID.

**Ограничения v3.0 (начальная защита, не замер производительности):** `payloadCellCount <= 512`, `blockCount <= 64`, `blockLength <= 255` ячеек, общая длина не более `521` логической ячейки. Пределы будущих layout/физических строк ещё предстоит проверить. Отсечь некорректные значения **до** выделения памяти.

## 4. Формат типизированного блока

Каждый блок: **одна ячейка-заголовок** `(blockType: u8, dataCellCount: u8, blockFlags: u8)`, затем ровно `dataCellCount` следующих RGB-ячеек. Никаких неявных смещений. Сумма `1+dataCellCount` по блокам обязана совпадать с `payloadCellCount`. Дубли обязательных блоков запрещены, порядок по возрастанию `blockType`; неизвестные optional-блоки можно пропускать по длине, но неизвестный обязательный блок — отвергать/отмечать неподдерживаемую модель.

`blockFlags`: bit0 = **critical** (непонятный тип/ревизия => reject); остальные биты зарезервированы и должны быть нулём в версии 0.1 спецификации. `dataCellCount=0` допускается только для специально описанных zero-payload блоков; у Core это ошибка.

Черновой реестр типов:

| ID hex | Имя | Назначение |
|---|---|---|
| 01 | CORE | HP игрока/цели, ресурс, основные состояния и validity |
| 02 | CAST_GCD | GCD, каст/канал, время окончания, прерываемость |
| 03 | AURAS | словарь отслеживаемых аур + стаки/remaining/known |
| 04 | SPELLS | доступность, кулдауны, заряды, SpellID через словарь |
| 05 | ITEMS | инвентарь, слоты 13/14, лечебные предметы |
| 06 | PET | HP/состояние/цель питомца |
| 07 | RANGE_AOE | проверка дальности умения, приблизительный AoE |
| 08 | PARTY_RAID | лечение/диспел/роли и известность |
| 09 | PVP | арена, контроль, DR, иммунитет, тринкет |
| 0A | ENCOUNTER | фазы, таймеры, события DBM |
| 0B | CAPABILITIES | доступные блоки, источники и ревизии словаря |

**Только `01 CORE` имеет детальное поле битов в этом черновике.** Значения 02..0B зарезервированы — реализация без последующей спецификации каждого блока недопустима. Для данных PvP/BossMod наличие типа не доказывает доступность нужного API.

## 5. CORE block v0.1: строгое описание для первых тестовых кадров

`blockType=01`, `dataCellCount=03`, `flags=00` для первых тестовых кадров (в рабочем профиле можно сделать critical=01). Следующие **три** ячейки:

| Ячейка CORE | R | G | B |
|---|---|---|---|
| data0 | playerHpPercent (0..100; FF unknown) | targetHpPercent (0..100; FF unknown) | powerType (00..FE; FF unknown) |
| data1 | playerPowerPercent (0..100; FF unknown) | playerFlags bitmask | targetFlags bitmask |
| data2 | playerKnownMask | targetKnownMask | reserved=00 |

`playerFlags`: bit0=inCombat, bit1=dead, bit2=moving, bit3=casting. `targetFlags`: bit0=exists, bit1=hostile, bit2=dead, bit3=casting, bit4=interruptible, bit5=inAbilityRange. Для каждого булева флага **соответствующий бит KnownMask = 1 только при проверенном доступном значении**. Когда bitKnown=0, состояние НЕИЗВЕСТНО при любом бите значения. Оставшиеся биты = 0. `unknown` не приравнивать к `false`. Процентное значение FF означает Unknown/Unsupported; дальнейшее различение причин будет отдельным capabilities/status блоком.

Это пример минимального snapshot для тестирования транспорта, а не достаточное описание полной ротации. Детализация HP, фактической мощности ресурса, дистанции и других условий будет добавляться только с обоснованным разрешением/TTL.

## 6. CRC16 — точная схема тестовых кадров

Алгоритм **CRC-16/CCITT-FALSE**: width=16, poly=`0x1021`, init=`0xFFFF`, refin=false, refout=false, xorout=`0x0000`. Стандартный check для ASCII `"123456789"`: **`0x29B1`**.

**Область расчёта:** конкатенация R,G,B логических ячеек `4..` **до CRC footer**, то есть Header0/Header1/Header2/Header3 + все payload-ячейки, без четырёх маркеров и без footer. CRC на исходных **байтах**, до обработки графического/цветового масштаба. В footer `CRC hi`, `CRC lo`, `sequence copy`. Decode rejects: CRC mismatch, sequence mismatch, invalid length, impossible type, wrong schema.

**Проверочные векторы (CRC независимо рассчитан CRC-16/CCITT-FALSE):**

### Vector A — корректный кадр №1

```text
0: FF 00 FF   1: 00 FF 00   2: FF FF FF   3: 00 00 00
4: 03 01 00   5: 01 12 34   6: 00 04 01   7: 01 01 00
8: 01 03 00   9: 3C 5A 00  10: 32 08 03  11: 01 03 00
12: 1F 55 01
```

`profileHash=0x1234`, Forever, seq=1, 1 CORE block, payload=4 cells. PlayerHP=60%, targetHP=90%, powerType=0, power=50%; playerFlags=0x08, playerKnown=0x01 (известен только inCombat=false; casting=1 остаётся **unknown**), targetFlags=0x03, targetKnown=0x03 (exists/hostile=true; прочее неизвестно). CRC=`0x1F55`.

### Vector B — корректный кадр №2

```text
0..3: same markers
4: 03 02 00   5: 01 12 34   6: 00 04 01   7: 01 01 00
8: 01 03 00   9: 37 5A 00  10: 30 08 03  11: 01 03 00
12: 3F B3 02
```

Seq=2, playerHP=55%, power=48%, CRC=`0x3FB3`. Декодер должен принять и определить новый sequence.

### Negative vectors

1. В Vector A заменить byte `cell9.R`: `3C→3B` без пересчёта CRC — **reject CRC**.
2. В Vector A заменить `cell12.B`: `01→02` — **reject sequence mismatch**.
3. В Vector A заменить `cell6.G`: `04→05` — **reject length/block-count** (также возможен CRC mismatch; ошибка длины должна быть обнаружена до чтения вне массива).
4. В Vector A заменить `cell4.R`: `03→02` — **reject unsupported protocol version**.
5. В Vector A заменить `cell4.B`: `00→01` — **reject unsupported encoding**.
6. В Vector A заменить `cell5.R`: `01→02` при Forever profile — **reject incompatible client**.
7. В Vector A заменить `cell10.G`: `08→00` и корректно пересчитать CRC — проверка `playerKnownMask=0x01` обязана давать всё ещё known `inCombat=false`; неизвестное `casting` не должно считаться false.

Это тесты **спецификации и самостоятельно рассчитанных данных**, а не запись реально переданных кадров WoW.

## 7. Профили, capabilities, кодирование и масштаб

- Manifest конкретного клиента фиксирует `clientFamily`, `schemaRevision`, `capabilitiesRevision`, `profileHash`, маппинг spell/item/aura indexes, `cellsPerRow`, пределы, поддерживаемые блоки, режим калибровки, правила TTL.
- Внешние XML для разработки и аддоны остаются отдельными по клиентам; runtime XML-ротации в будущем поставляются как ресурсы **одного** EXE. Никакого переноса чужих `yaml.enc`.
- Текущий wire v3.0 использует **direct8**. Вариант stepped4, аналогичный по смыслу референсу Sertyrew (4-bit каналы с шагом 17), будет отдельной ревизией; при описании потребуется явно указать порядок 2 nibble на байт, количество физических ячеек, начало несжатых маркеров и устойчивость к цветокоррекции. До этого `encoding=1` недействителен.
- Не угадывать DPI/масштаб по одному кадру. Разработать калибровочный тест: фактическая высота, `UIParent:GetEffectiveScale()`, режим экрана; измерить физический pitch для нескольких UI Scale и оконных режимов.
- Контроль высоты/длины полоски и пересечения с чужими UI-элементами. Не считать `3 physical pixels` автоматически надёжными во всех конфигурациях.

## 8. Доставка свежих состояний и XML-движок

Сбор Lua по событиям **и** при необходимости лёгкий `OnUpdate` для изменяющихся полей; расписание разных TTL: касты/HP/GCD быстрее, редко меняющиеся характеристики и таланты — медленнее. Никакой гарантии latency без замеров. Windows отделяет транспортный поток от WPF Overview, отвергает невалидные/устаревшие данные, хранит один атомарный последний валидный snapshot с отметкой времени. Для будущих XML-условий availability must propagate: `KnownTrue`, `KnownFalse`, `Unknown`, `Unsupported`, `Stale`.

Предполагаемые блоки PvP (DR, касты, иммунитет, аксессуары), Items (поты, камни, trinket slot 13/14), Encounter (DBM) закладываются **заранее**. Подробные версии этих блоков будут созданы до внедрения, отдельно от бинарного формата CORE.

## 9. Проверки перед первым коммитом кода

- Совпадение Vector A/B и негативных тестов Lua encoder / C# decoder.
- Отказ от неизвестных protocol/encoding/schema/client/profile/hash.
- Проверка длины, уникальности/порядка блоков, предельного числа ячеек, корректности CRC и различия unknown/false.
- Эмуляция пропуска, дублирования и переполнения sequence (255→0), stale/timeout, рассинхронизации header/footer.
- Тест на 3-4 конфигурациях UI Scale/DPI и стандартном режиме окна; реальный pitch и процент неверно прочитанных кадров.
- Измерение `event→Lua→render→capture→decode→state` и CPU/GUI responsiveness. **150 мс интервал в v2 — не гарантия v3**.
- Отдельный контролируемый выпуск `*-dev` для v3 и сохранение возврата на проверенный `0.1.13-dev`.
