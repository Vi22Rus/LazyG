# LazyG 0.4.0-dev — встроенные ротации и настройки специализаций (ПЛАН, НЕ РЕАЛИЗАЦИЯ)
Дата решения: 2026-11-19. Клиент первой версии: **WoW Forever**. Главная ветка: `Vi22Rus/LazyG:main`.

## Решение по архитектуре

LazyG — **одна программа Windows (.NET 8 Avalonia в текущем репозитории)** с собственными встроенными ротациями и отдельными Lua-адаптерами под разные версии WoW. **Ближайший ориентир — WarMate**, а не Aster: правила и приоритеты принадлежат LazyG, пользователь не обязан ставить Hekili/JustAC/MaxDps. Aster остаётся референсом для абстракций источников рекомендаций и диагностики, НЕ архитектурой обязательных провайдеров.

**Не делать визуальный редактор XML для пользователя.** Разработчики поддерживают версионированные XML-ротации; EXE содержит проверенный комплект. Пользователь видит WarMate-подобную страницу **настроек конкретной специализации**, не редактирует последовательность заклинаний вручную.

### Основное требование: настройки извлекаются из реальных правил

Если XML-ротация содержит осмысленный регулируемый порог, задержку, интервал или переключаемое поведение (например, использовать способность при ресурсе не ниже/не выше N, HP ниже N%, запас времени дебафа N секунд, порог AoE, включение автоатаки, допустимый запас до кулдауна, приоритет защитного заклинания), это значение объявляется **параметром ротации** с типом, единицей, значением по умолчанию, диапазоном, шагом, описанием и ссылками на реальные использующие его правила.

UI генерируется из **той же схемы параметров**, что проверяет движок. **Никаких двух разъехавшихся списков:** каждому контролу соответствует ключ параметра, используемый хотя бы одним правилом; каждая ссылка на параметр должна существовать и иметь совместимые тип/единицу; отсутствие ссылки/лишний контрол — ошибка валидации. Принцип: *пользователь меняет порог без правки XML*, изменение влияет на оценку правил без пересборки EXE, а `Reset to defaults` возвращает оригинал.

Не выводить настройки для технических констант, SpellID, строгих инвариантов безопасности, внутренних RGB протоколов, защитных проверок цели/живости/клиента и непонятных/неработающих параметров. Не придумывать произвольные пороги без игрового обоснования. Для значений, доступность которых не подтверждена в Forever, UI маркирует **requires signal / Unknown/Unsupported**; отсутствие сигнала **никогда** не превращать в разрешение способности.

## Целевые подсистемы этапа 0.4.0-dev

1. **Rotation Registry & Profile Catalog.** Строго версии клиента (`forever` отдельно от 3.3.5), класса, специализации, PvE/PvP, версии XML; выбор по проверенным ClassId/SpecIndex с Unknown fallback (нет автоматического подбора «похожей»). Базовые XML встраиваются как ресурсы EXE; внешние XML по умолчанию не нужны. Встроенные профили различаются состояниями `Implemented/Tested/Unavailable/Experimental`; не помечать весь каталог рабочим до игрового теста.
2. **XML v2 схема + безопасный parser/validator.** Отдельные группы правил (обычная ротация, прерывания, защитные, AoE, поддержание эффектов, режимы боя), приоритеты, типизированные условия AND/OR/NOT, запрос значения параметра, ссылки на способности по SpellID и рангу, метаданные профиля, строгие пределы размера/глубины/числа правил, запрет DTD/внешних сущностей. Сохранить старый диагностический v1 пример и его тесты; использовать явную миграцию/версию, не менять его интерпретацию молча.
3. **Settings Schema.** Для каждого параметра `id`, тип Boolean/Integer/Decimal/Enum, единица %, секунды, число целей, ресурс, способ отображения Toggle/Slider/Select, min/max/step/default, категории Essentials/Advanced, PvE/PvP scope, RU/EN label, help/tooltip, список RulesUsingKey, capability requirement, help для Unknown. Типизированные значения вместо строк; проверка межзависимых порогов (например, min<=max) и недопустимых значений.
4. **Настройки по специализациям.** Сначала выбор класса/спека, внутри страницы как у WarMate: Essentials/Advanced, PvE/PvP, поиск по настройкам, Changed only с количеством изменений, Reset to defaults (отдельный режим, подтверждение), Toggle и Slider, группы Rotation/AoE/Cooldowns/Defensives/Interrupts/Utility. Показывать только настройки, реально применяемые текущими правилами. Недоступные сигналы отображать явно; без фальшивых активных ползунков.
5. **Persistence & rollback.** Значения настроек как overrides относительно встроенных defaults, локально, отдельно для клиента/класса/спека/режима; атомарная запись, чтение с валидацией, сохранение при обновлениях, обработка миграций и неизвестных ключей, резервная копия и восстановление defaults. Никогда не перезаписывать встроенный XML пользовательскими настройками.
6. **Rotation evaluator.** `GameState`+правила+resolved settings, трёхзначная логика `True/False/Unknown` с причинами `Protected/Stale/Unsupported`, приоритеты, порядок конфликтующих правил и режимы AoE/PvP/прерываний. Отдельный результат **Recommendation** и отдельная проверка **CanExecute**; на этапе 0.4.0-dev нет новых автоматических нажатий. Глобальные проверки живой враждебной цели, принадлежности клиенту и свежести не могут быть отключены настройкой.
7. **Diagnostics / Rule Trace.** По каждому правилу: выбранный SpellID, источник профиля, условия, исходное/эффективное значение порога, качество/возраст сигнала, причина блока, причастные параметры. Агрегированные счётчики Unknown/Unsupported/Stale и подсказка «какого RGB сигнала не хватает»; отчёт JSON без скриншотов и приватных игровых данных; возможность Copy/Save. Не спамить событиями на каждый кадр.
8. **Offline simulator & regression.** Искусственные снимки по фазам боя, проверка приоритетов, PvE/PvP-разделения, минимальных/максимальных порогов, выключения способности, AND/OR/NOT, дебафа, GCD/CD, плохих входов XML, отсутствующих сигналов, старых снимков, восстановления/сохранения defaults, RU/EN labels. Предварительные snapshot тесты каждой реальной ротации; CI-проверка что *все параметризованные ссылки объявлены и реально используются*.
9. **Data/rotation content boundary.** Для начала реализовать engine и полноценную эталонную Forever-специализацию как сквозную проверку; затем отдельным крупным этапом наполнить все специализации на основании WoW механики + Sonah/NAG/других источников, **не копируя защищённый код**, и регулярно расширять параметры на основании реальных условий. Нельзя называть все классы готовыми по одной эталонной ротации.

## Классификация настроек

- **Полезные настраиваемые:** игровые пороги ресурса/здоровья, время поддержания бафа/дебафа, min target count для AoE, резерв ресурса, допуск до окончания эффекта, откладывать burst, включение опциональной способности, условие использования защитного кулдауна.
- **Системные ограничения, неизменяемые пользователем:** безопасная идентичность клиента, доказанная живость цели, пропуск `Unknown` при отсутствии данных, контроль RGB freshness, запрет отправки клавиш в диагностике, валидность SpellID/rank, пакетные CRC.
- **Параметр есть в XML, но нет подтверждённого источника Forever:** оставить доступным для симулятора и явно показать статус Unsupported/Unknown. В живом игровом режиме условие не даёт `True` без верифицированного сигнала.
- **Желательно не показывать вообще:** константы, не влияющие на поведение, внутренние ID и низкоуровневую конфигурацию протокола.

## Предлагаемый формат ссылки (эскиз, НЕ внедрённая схема)

```xml
<Setting id="heroicStrikeRageMin" type="int" unit="rage"
         default="70" min="0" max="100" step="5"
         ui="slider" group="Rotation" tier="Advanced"/>
<Rule spellId="78" priority="120" enabledBy="heroicStrikeEnabled">
  <Condition signal="PlayerRage" compare="GreaterOrEqual"
             settingRef="heroicStrikeRageMin"/>
</Rule>
```

**Это только концептуальный пример, не проверенная ротация, не утверждение доступности ярости и не финальный SpellID для Forever.** Реальные игровые SpellID, ranks, API и пороги подтверждаем по клиенту/источникам. Настройка единицы `rage` не может быть случайно подставлена вместо процента маны/HP; UI показывает точные единицы.

## Рабочий процесс без десятков загрузок

- Сначала в новом чате проверить GitHub `LazyG/PROJECT_CONTEXT.md`, `LazyG/CHANGELOG.md`, этот план и текущие исходники, а также доступные Sonah/WarMate/Aster/JustAC/NAG из файлов проекта.
- Спроектировать схему, реализовать полный модуль, покрыть автоматическими тестами, исправить CI без привлечения пользователя, завершить документацию.
- **Только один стабильный CI-PASSED dev комплект** для общего пользовательского тестирования после всех автоматических проверок. Не называть релизом.
- До модификаций оценить scope и сохранить GitHub run `0.3.0-dev` для rollback. Не портить доказанную работу RGB. Интеграция с фактическим вводом клавиш — отдельный этап после подтверждения данных.
