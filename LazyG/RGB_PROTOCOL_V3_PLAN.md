# LazyG — план RGB-протокола v3 по архитектурной модели WarMate/Sertyrew

**Дата решения:** 2026-11-18  
**Статус:** `[PLANNED]` — архитектурное техническое задание, не реализованное в коде.  
**Проект:** `Vi22Rus/LazyG`, `main`.  
**Рабочая Windows-версия на момент обсуждения:** `0.1.13-dev` (RGB v2, быстрый опрос). Пользователь подтвердил быстрое обновление состояний; это **не** подтверждение существования v3.  
**Обязательные сопутствующие документы:** [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md), [CHANGELOG.md](CHANGELOG.md). **Черновик wire-формата, CRC и тестовые векторы:** [RGB_PROTOCOL_V3_SPEC_DRAFT.md](RGB_PROTOCOL_V3_SPEC_DRAFT.md).

## 1. Цель и неизменные решения

Построить собственный расширяемый RGB-транспорт LazyG, опирающийся на **модель архитектуры WarMate + Lua-аддона Sertyrew**. В качестве основного ориентира рассматриваются отделение сбора игровых состояний от принятия решений, форматирование/кодирование пакета, защита целостности, кадровая свежесть, адаптация полоски к масштабу, профильные блоки игровых фактов. Не копировать сторонний программный код, бинарные компоненты, защищённые ротации и интерфейс.

- **Один общий Windows EXE** на C#/.NET 8 WPF для различных официальных и частных клиентов WoW; сначала Forever, затем 3.3.5 и другие.
- **Отдельный Lua-адаптер для каждой версии WoW.** Lua получает только реально доступные поля WoW API и упаковывает их в RGB; не хранит полные ротации и не рассчитывает приоритеты.
- **Общий Windows Core** считывает, валидирует и нормализует пакет; **Windows XML-движок** выбирает действие. По каждому клиенту — отдельные XML-ротации, встроенные ресурсами в единый EXE.
- Любой источник данных сообщает не только значение, но и его *доступность/достоверность*. «Неизвестно», «не поддерживается», «устарело», «ложь» — разные состояния.
- Сохранить проверенный RGB v2 и возможность отката. Внедрение v3 — отдельная новая `*-dev` с тестированием, не замена существующей рабочей ветки без проверки.
- Цель — полноценные PvE/PvP-ротации, лечебные/защитные действия, аксессуары, хилпоты, дистанция, касты, события боссов и расширение классов без изменения общего EXE-движка.

## 2. Разграничение проверенного и предлагаемого

**Изученный образец:** Sertyrew содержит модули `Collect`, `Protocol`, `Output`, `Profile`, `Compat`; в ранее исследованных файлах отмечены `Protocol.lua`, `Encode.lua`, `Bits.lua`, `Crc16.lua`, `Layout.lua`, `Strip.lua`, `FrameAnchor.lua`, `Encounter.lua`. В архитектурном обзоре зафиксированы варианты кодирования `direct8`/`stepped4`, CRC16 (полином `0x1021`), счётчик кадров, базовая и расширяемая раскладка, логика пересчёта полоски относительно масштаба и сигналы DBM. **При реализации каждую деталь нужно снова сверить с точными файлами и конкретной версией Sertyrew.**

**WarMate.exe:** предоставлен бинарный референс. Не запускать и не приписывать ему неподтверждённые внутренние алгоритмы. Конкретная схема взаимодействия EXE с Lua, содержимое зашифрованных `*.yaml.enc` и внутреннее исполнение ротаций **не доказаны** статическим наличием соответствующих строк.

**Собственный текущий RGB v2 LazyG:** 9 ячеек в одной строке, `4×4` UI-ед., шаг 5, протокол с идентичностью игрока, веткой талантов и четырьмя флагами. В `0.1.13-dev` Windows делает попытку чтения каждые 150 мс. Пользователь сообщил, что обновление стало быстрым. Протокол v3, CRC16 v3, дополнительные блоки и XML-движок **ещё не написаны**.

**Предложения v3 ниже — не утверждённый бинарный wire-format.** Количество физических ячеек, порядок байтов, CRC initial value, таблица block IDs, частоты и пределы длины будут зафиксированы отдельно до кодирования после оценки пропускной способности и API WoW Forever.

## 3. Поток данных

```text
WoW Forever / WoW 3.3.5 / ... 
  -> клиентский Lua: Collect (игровые факты) + Compat (возможности/API)
  -> нормализация и snapshot (значение, наличие, время/возраст, идентификатор)
  -> RGB Encoder: marker + header + typed data blocks + frame counter + CRC16
  -> полоса RGB в пределах доступной клиентской области WoW
  -> общий Windows Capture / Decode / Validate / Normalize
  -> GameState snapshot с Known/Unknown/Unsupported/Stale
  -> XML Rotation Engine внутри LazyG.exe
  -> рекомендация действия / связанная клавиша (будущая реализация)
```

Обновление текста Overview отдельно от частоты приёма пакетов и ротационного цикла. Не выполнять многократный блокирующий захват экрана из UI-потока; исключать параллельные захваты.

## 4. Предлагаемые слои wire-протокола v3

### 4.1. Калибровка и обнаружение

- Явные цветовые маркеры начала и конца и проверка размера шага, цвета, положения, формата кодирования.
- Пересчёт размеров полоски с учётом WoW UI Scale, эффективного масштаба и физической плотности/разрешения; обработка смены режима окна, DPI и масштаба без обязательного сброса графических настроек.
- Не полагаться на фиксированный экранный прямоугольник на произвольных конфигурациях; минимизировать покрываемую область и влияние оверлеев.
- Учитывать, что текущий захват основан на видимой игровой области активного окна: фоновые/эксклюзивные режимы не считать автоматически поддерживаемыми.

### 4.2. Header — предложение

Маркеры, magic/идентификатор LazyG, **версия протокола**, ID версии/семейства клиента, совместимый профиль/capabilities, режим цветового кодирования, длина полезной нагрузки, номер кадра/sequence, набор блоков/их типы. Поля и диапазоны ещё подлежат спецификации. Windows не должен декодировать пакет неподходящей версии или несовместимого профиля.

### 4.3. Typed data blocks — предложение

- `core/player`: идентичность класса/специализации, уровень, флаги боя, движение, HP/MaxHP, тип и величина ресурса.
- `target`: наличие, враждебность, жизнь, HP, тип, дистанция/проверки дальности, каст/канал, время до конца, прерываемость.
- `combat`: GCD, активный каст, текущий cooldown/charges, известные способности, стоимость, последняя попытка/ошибка.
- `auras`: полезные баффы/дебаффы, ID, стеки, оставшаяся длительность, источник/владелец (если доступно), проки.
- `items`: доступность предметов, аксессуаров в слотах 13/14, хилпотов, камней здоровья, общий предметный cooldown.
- `pet`: наличие/жизнь/HP/цель/состояние питомца.
- `enemies/aoe`: доступные оценки числа противников/контекст AoE и их валидность.
- `party/raid`: потребности исцеления, роли, доступные дебаффы для снятия, сведения о группе.
- `pvp`: арена, касты противников, контроль, DR, иммунитеты, состояние PvP-тринкета, опасные кулдауны, снятие эффектов.
- `encounter`: стадия боя, таймеры и предупреждения BossMod, идентификатор события и время до него.

Это **каталог возможностей**, а не обещание наличия каждого поля в конкретном WoW API. PvP-сведения о противниках и точная дистанция могут быть неизвестны либо недоступны; недоступное поле нельзя подменять нулём.

### 4.4. Payload и профильный словарь

Планируется **компактная адресация**: вместо полного текстового имени/SpellID в каждом кадре передавать согласованные индексы/словари состояния по клиенту, классу, специализации и профилю. Грамотно группировать часто изменяющиеся факты и редкие данные. Версии словаря должны быть согласованы между Lua и EXE.

Для будущего XML-движка необходимо обеспечить достаточные факты для оценки *всего списка приоритетов*; недопустимо экономить RGB, отбрасывая нужные условия без явного сообщения. Динамический выбор пакетов не должен зависеть от того, какое действие Windows выбрал в предыдущем кадре, если это создаёт слепые зоны.

### 4.5. Freshness и Integrity

- Frame/sequence counter; фиксировать пропущенные, дублированные и зависшие кадры.
- CRC16 как модель защиты целостности, с собственным точно описанным wire-format (полином `0x1021` по изученному референсу; начальное значение и покрытие согласовать до реализации).
- **Атомарный snapshot**: не объединять разные непроверенные моменты игры в одну «достоверную» рекомендацию. Измерить риск частично перерисованной RGB-полоски и предусмотреть обнаружение.
- Контроль длины, типа и порядка блоков, допустимых диапазонов; при ошибке — отказ от рискованной рекомендации.
- Статусы `Known / Unknown / Unsupported / Stale`, сроки годности отдельных измерений (например, HP, касты, кулдауны).
- Отдельно измерить end-to-end latency: игровое событие → обновление Lua → рендер RGB → захват Windows → декодер → модель состояния → рекомендация.

## 5. Требования будущих XML-ротаций

Ротации хранятся в собственных XML исходниках в GitHub и встраиваются как ресурсы в **единый LazyG.exe**. Никакого исполнения Lua-ротаций в аддоне. Нужны предикаты `AND/OR/NOT`, сравнения, альтернативные цели, кулдауны/GCD/заряды, стоимость ресурсов, ауры/стеки/время, движение/дистанция, питомец, одиночные и AoE-приоритеты, PvE/PvP, расовые умения и условия защитных действий.

Для расходников: хилпоты, камни здоровья, аксессуары, PvP-trinket, настраиваемые HP-пороги, запрет повторных попыток во время общего кулдауна, проверки наличия и готовности. Для PvP: контроль, снижение эффективности контроля (DR), снятие эффектов, иммунитеты, опасные касты, приоритеты прерывания. Для PvE: рейдовый урон, танковые события, механики босса и лечение союзников. **Референс полноты Forever — Sonah**, но не копировать защищённые фрагменты.

Ротационный движок должен уметь объяснить, почему выбрал/не выбрал действие, какие факты неизвестны и какова свежесть данных. Не выдавать уверенную рекомендацию при некорректном или устаревшем пакете.

## 6. BossMod / DBM

По предыдущему разбору Sertyrew, `Collect/Encounter.lua` связывает интерфейс со следующими событиями DBM: `DBM_TimerBegin`, `DBM_TimerUpdate`, `DBM_TimerStop`, `DBM_Pull`, `DBM_SetStage`, `DBM_Kill`, `DBM_Wipe`. Для LazyG нужен отдельный **Encounter Adapter** (не в общем ядре игрового API), преобразующий доступные события в типизированные факты: стадия, идентификатор события, таймер, оценка времени до способности, статус боя с боссом. Требуется определить, какие метки означают угрозу/урон/сброс DPS: одни только названия событий не доказывают эту семантику.

Первая цель — DBM. Поддержка BigWigs — отдельное исследование; не объявлять её реализованной или автоматически совместимой.

## 7. Разделение ответственности и безопасность совместимости

- `WoW Forever adapter` — только API и нормализация Forever (например, `C_Traits`, `C_ClassTalents` и доступные protected/secret values).
- `WoW 3.3.5 adapter` — отдельный API/TOC/словарь, несовместимые значения не приравнивать к Forever.
- `Windows transport` — обнаружение полоски, декодирование, валидация, отчёт о телеметрии, независимые снимки данных.
- `Windows XML engine` — общий интерпретатор правил, не список жёстко прошитых классов.
- `Profile manifest` — версия клиента/аддона/протокола, capabilities, словарь SpellID/itemID, требуемые блоки, совместимость с XML.
- Не пытаться использовать память процесса WoW как скрытый источник данных.
- Не повреждать проверенный RGB v2 и не перезаписывать существующие папки аддонов автоматически без осознанной миграции.

## 8. Этапы и критерии приёмки

1. **Спецификация транспорта v3 (без ротаций):** определить окончательную раскладку, битовые поля, блоки, кодирование direct8/stepped4, CRC, sequence, границы и допустимую производительность; тестовые векторы кодер/декодер. Приёмка: идентичная интерпретация тестовых пакетов C# и Lua, отказ при ошибках и несоответствии версии.
2. **Рабочий v3 в Forever:** калибровка и масштабирование, базовая телеметрия HP/ресурс/цель/GCD/каст; тест в реальном WoW при обычном UI Scale. Приёмка: изменение значений без ошибочных пакетов и понятный вывод `Unknown`.
3. **Боевые данные:** ауры, кулдауны, предметы, питомец, дистанция и список поддерживаемых способностей. Приёмка: сценарии доступно/неизвестно/запрещено API/нет предмета.
4. **PvP, группа и рейд:** арена, контроль/DR, хил, снятие эффектов, AoE, серьёзные ограничения API. Приёмка: матрица поддерживаемых полей по версии клиента.
5. **BossMod:** проверить реальную передачу DBM events и семантику таймеров, обработку отключённого DBM. Приёмка: корректная работа при наличии и отсутствии BossMod.
6. **XML-движок и наборы правил:** схема, валидатор, интерпретатор, встроенные ресурсы XML, диагностика условий. Приёмка: проверенные сценарии Forever (Hunter BM → MM → Survival → другие классы), затем отдельные наборы 3.3.5; полноценность всех классов не объявлять до отдельных тестов.

**Порядок внедрения:** этап 1 — следующий; после него только по явной команде пользователя переходить к изменениям исходников. Каждое изменение — `*-dev`, коммит в `main` по запросу, проверка GitHub Actions, ссылка на конкретную сборку, команда PowerShell для единого EXE, запись в `PROJECT_CONTEXT.md` и `CHANGELOG.md`. Пользовательские PASS фиксировать отдельно от CI.

## 9. Открытые проектные вопросы перед реализацией

- Точный размер, топология и лимит количества RGB-ячеек для v3; физические vs UI-пиксели.
- Фиксированная базовая часть или исключительно TLV-блоки; допустимая частота смены раскладки.
- Wire-format полей, типы значений и шкалы квантования, endian, CRC seed/coverage.
- Формат словаря интересующих аур/способностей, версионирование capabilities и правила синхронизации XML с источником данных.
- Отдельные таймеры для UI, транспортного захвата и обновления GameState; допустимая CPU-нагрузка.
- Управление фокусом окна WoW и работа в разных графических режимах.
- Правила snapshot-согласованности, TTL, пропуска/повтора кадров.
- Какие конкретные игровые факты Forever реально доступны без protected/secret ограничений.
- Что именно передаётся из DBM и что можно безопасно считать событием для ротации.

Для `0.1.14-dev` сделаны отдельные Lua encoder и C# decoder с тестовым harness. Они не подключены к боевому/экранному потоку; RGB v2 остается контрольной точкой, `0.1.13-dev` сохранена для отката. Следующий этап — профиль/визуальный вывод Forever v3, CI и проверка в игре.
